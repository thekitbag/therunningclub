# Deployment playbook — rmpac.co.uk

A step-by-step runbook for taking RMPAC from this repository to a live site on
`https://rmpac.co.uk`.

Work through the phases in order. Each has a check that must pass before you
move on, so a failure is caught next to its cause rather than three steps later.

Roughly 60–90 minutes, most of which is waiting for DNS.

---

## Before you start

You need:

|                                 |                                                                                                          |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A Render account                | <https://render.com> — the free tier is enough to create the blueprint, but see the plan note in Phase 2 |
| Access to the `rmpac.co.uk` DNS | Wherever the domain was registered                                                                       |
| GitHub access                   | `github.com/thekitbag/therunningclub`, with permission to merge                                          |
| A password manager              | For the first administrator password                                                                     |

Two decisions to make now, because they are awkward to change later:

**Which hostname is canonical?** This playbook uses the apex, `rmpac.co.uk`,
with `www` redirecting to it. If you prefer `www` as canonical, swap them
consistently — `APP_ORIGIN` must match whichever one visitors actually land on,
or every admin form submission will be rejected by the same-origin check.

**Which database plan?** This decides whether you have backups. See Phase 2.

---

## Phase 1 — Get the code onto `main`

The blueprint watches `main`, but the application is on `feat/v1-app`. Until it
is merged, Render will deploy the initial commit and nothing will work.

```bash
gh pr create --base main --head feat/v1-app \
  --title "RMPAC v1" \
  --body "Initial application. See README.md."
```

Review it, then merge. Or, if you would rather not review a PR:

```bash
git checkout main
git merge feat/v1-app
git push origin main
```

**Check:** `git ls-remote --heads origin main` returns the same SHA as your
local `main`, and `render.yaml` exists on `main`.

---

## Phase 2 — Create the Render services

In the Render dashboard: **New → Blueprint**, choose the
`thekitbag/therunningclub` repository, and let it read `render.yaml`.

It creates two things:

- **`rmpac`** — the Node web service
- **`rmpac-db`** — the managed PostgreSQL database

Both are in Render's **Frankfurt** region, which is the closest to Dorset that
Render offers. Keeping the service and database in the same region matters more
than the region itself: it lets them talk over the private network instead of
the public internet.

> **Decide the database plan before continuing.**
>
> The blueprint requests `basic-256mb`. Whether that plan includes automated
> backups, and for how long, is Render's policy and it changes — **check
> Database → Backups in the dashboard and confirm what you actually have.**
>
> Do not take this document's word for it, and do not assume. If the plan you
> chose has no automated backups, you are relying entirely on the manual dumps
> in the Ongoing section, and you should know that now rather than after an
> incident.

**Check:** both services appear in the dashboard. The first deploy may fail at
this point — that is expected, because configuration is not finished.

## Phase 3 — Configuration

Most values come from the blueprint. `DATABASE_URL` is wired from the managed
database automatically, and `SESSION_SECRET` is generated by Render on first
deploy — you never see or set it.

Confirm these on the `rmpac` service under **Environment**:

| Variable            | Value                                            | Source    |
| ------------------- | ------------------------------------------------ | --------- |
| `APP_ORIGIN`        | `https://rmpac.co.uk`                            | blueprint |
| `JUSTGIVING_URL`    | `https://www.justgiving.com/page/mark-mike-pspa` | blueprint |
| `NODE_ENV`          | `production`                                     | blueprint |
| `NODE_VERSION`      | `24`                                             | blueprint |
| `ALLOW_SAMPLE_SEED` | `false`                                          | blueprint |
| `DATABASE_URL`      | _(from `rmpac-db`)_                              | automatic |
| `SESSION_SECRET`    | _(generated)_                                    | automatic |

### Set the club passcode

`SITE_PASSCODE` gates the whole public site, so members' names and times are not
on the open internet. Choose something a member can repeat over the phone —
length matters more than symbols.

**The service will not start without it.** That is deliberate: a deployment that
booted without a passcode would publish exactly the data it protects.

Rotating it later signs every device out, so tell members first. See
[`privacy-gate.md`](privacy-gate.md).

Optionally set `CLUB_WELCOME_COPY` and `FUNDRAISING_COPY` to override the
built-in home-page text. Plain text, no markup.

**Do not set the `BOOTSTRAP_ADMIN_*` variables yet.** They come in Phase 6 and
are removed immediately afterwards.

### What happens if you get this wrong

The application validates its whole configuration at startup and **refuses to
boot** if anything is missing, still a development placeholder, or if
`APP_ORIGIN` is not HTTPS. A misconfigured deploy therefore fails its health
check and never receives traffic, rather than serving in an unsafe state.

The service log will name the offending variables directly, for example:

```
RMPAC failed to start.

Invalid application configuration:
  - SESSION_SECRET is still the development placeholder.
  - APP_ORIGIN must use https in production.
```

## Phase 4 — First deploy

Trigger a deploy (**Manual Deploy → Deploy latest commit**) and watch the log.
Three things happen, in this order:

1. **Build** — `npm ci && npm run build`
2. **Pre-deploy** — `npx prisma migrate deploy` creates the schema. This runs
   _before_ the new instance takes traffic, so a failed migration fails the
   deploy instead of leaving a half-migrated database serving requests.
3. **Start** — `npm run start`, then Render polls `/api/health` until it passes.

**Check:**

```bash
curl -s https://rmpac.onrender.com/api/health
```

Expect:

```json
{ "status": "ok", "configured": true, "database": "ok", "durationMs": 12 }
```

`"database":"unavailable"` means the service cannot reach PostgreSQL — check
that `DATABASE_URL` is bound to `rmpac-db` and that both are in the same region.

The site is live at this point, on Render's own `.onrender.com` hostname, with
an empty database. Visiting it will land you on the club passcode screen; enter
the passcode and every section will show its empty state. That is correct.

---

## Phase 5 — Custom domain and TLS

1. On the `rmpac` service: **Settings → Custom Domains → Add Custom Domain**.
2. Add `rmpac.co.uk`, then add `www.rmpac.co.uk`.
3. Render shows the DNS records to create. At your registrar, add them:
   - the apex as an `ALIAS`/`ANAME` record, or the `A` record Render gives you
   - `www` as a `CNAME` to the `.onrender.com` hostname
4. Wait for propagation. Usually minutes; occasionally an hour or more.
5. Render issues the TLS certificate automatically once DNS resolves.

**Check:**

```bash
curl -sI https://rmpac.co.uk | head -1        # expect HTTP/2 200
curl -s https://rmpac.co.uk/api/health        # expect status ok
```

`APP_ORIGIN` is already `https://rmpac.co.uk`, so nothing else needs changing.
If you decided to make `www` canonical instead, change `APP_ORIGIN` to match
now and redeploy — otherwise every admin form will be rejected.

## Phase 6 — Create the first administrator

There is no public sign-up and no "create the first admin" page, because a
publicly reachable one is a way to lose the site to whoever finds it first.

1. On the `rmpac` service, set these three under **Environment**:

   ```
   BOOTSTRAP_ADMIN_EMAIL     = you@example.org
   BOOTSTRAP_ADMIN_PASSWORD  = <a long passphrase, 12+ characters>
   BOOTSTRAP_ADMIN_NAME      = Your Name
   ```

2. Open **Shell** on the service and run:

   ```bash
   npm run bootstrap:admin
   ```

   Expect:

   ```
   Created administrator Your Name <you@example.org>.
   ```

3. **Delete all three variables** from the environment.

4. Sign in at `https://rmpac.co.uk/admin/sign-in` and change the password.

The command is idempotent — run it again and it reports that the account
already exists without touching it.

**Check:** you can sign in, and `/admin` shows the dashboard.

## Phase 7 — Load the club's real data

The production database starts empty. Everything below is done through the
admin interface — no shell, no spreadsheets, no developer.

> **Do not run any seed script against production.** Both seed scripts refuse to
> run when `NODE_ENV=production`, and the sample data carries placeholder dates
> of birth that would produce fabricated age-grade percentages against real
> members' names.

Suggested order, because each step depends on the one above:

1. **Administrators** (`/admin/administrators`) — add a second account, so one
   forgotten password is not a lockout. Disabling an account revokes its
   sessions immediately, on every device.

2. **Runners** (`/admin/runners`) — add each member with their **real date of
   birth**. This is the one piece of private data the club holds; it is used
   only to calculate age grades, and never appears on a public page, in a log,
   or in an offline cache.

   The form warns you about possible duplicates as you type.

3. **Time-trial season** (`/admin/time-trials`) — create Summer 2026, which
   fills in April–September and the 6 km / 8 km distances automatically. Add the
   six rounds with their real dates.

4. **Results** — open a round and enter the field. Remember the sheet records a
   handicap trial: enter the **actual running time (AT)**, not the handicap
   finish order. The application ranks by elapsed time, so its positions will
   differ from the sheet's numbering, and that is correct.

   Save, check the calculated scores, then use the impact preview before
   publishing. Publishing shows which later rounds and whose season totals will
   change before you confirm.

5. **Races** (`/admin/races`) — add fixtures. Tick "counts towards the club
   championship" for qualifiers; that creates the year's championship
   automatically.

6. **Championship** (`/admin/championships`) — publish the year once qualifying
   races have placings entered.

**Check:** the home page shows the next race and current leaders; the time-trial
and championship pages open the current season and year.

## Phase 8 — Go-live checks

Run these against the live site before telling the club about it.

- [ ] `curl -s https://rmpac.co.uk/api/health` returns `"status":"ok"`
- [ ] Home, Time Trial, Club Championship and Races all load without signing in
- [ ] The donate button opens **your** JustGiving page in a new tab
- [ ] Current standings are reachable from the home page in two taps on a phone
- [ ] **View source on a public page and search for a date of birth.** There
      must not be one. Search for `dateOfBirth` too.
- [ ] Sign in at `/admin`, then sign out
- [ ] Install the site to a phone home screen; it should open standalone
- [ ] Turn off data and reload a page you visited — it should show the cached
      copy _and_ an "You are offline" warning

The last two are the PWA behaviour. The offline warning matters: it is what
stops a stale table being mistaken for live results.

## Ongoing

### Releases

Merging to `main` deploys automatically. Before you merge anything:

```bash
npm run verify      # format, lint, types, unit, integration, production build
npm run test:e2e    # browser journeys and accessibility scans
npm run audit:prod  # production dependency advisories
```

CI runs the same checks on every pull request.

### Backups

Take a manual dump before any deploy that includes a migration:

```bash
pg_dump "$DATABASE_URL" --format=custom --file=rmpac-$(date +%Y%m%d).dump
```

Restore:

```bash
pg_restore --clean --if-exists --dbname="$DATABASE_URL" rmpac-YYYYMMDD.dump
```

**Restore one into a scratch database at least once.** A backup you have never
restored is a hypothesis, not a backup.

### Rolling back

Roll the service back from **Deploys → Rollback**.

Migrations do _not_ roll back with it, and this asymmetry matters:

- A migration that only **adds** tables or nullable columns is safe to leave in
  place while the code rolls back.
- A migration that **drops or renames** anything is not. You need the backup.

Because of that, prefer additive migrations, and deploy a destructive change
separately from the code that depends on it.

### Monthly

- [ ] Confirm backups are being taken, and that you can restore one
- [ ] Review `npm audit` and update dependencies
- [ ] Review `/admin/administrators` and disable accounts no longer needed

## Troubleshooting

**Build fails with `Cannot find module 'vitest'` or similar.**
The production build only type-checks application code; test files are excluded
via `tsconfig.json`. If you add a directory that imports dev-only packages, add
it to that file's `exclude` list and to `tsconfig.tooling.json`'s `include`.

**Deploy succeeds but the service will not start.**
Read the log for the `RMPAC failed to start` block — it names the offending
configuration variables. This is the fail-fast check doing its job.

**Admin forms rejected with "This form has expired."**
`APP_ORIGIN` does not match the hostname visitors are actually using. Most often
this is an apex/`www` mismatch. Make them agree and redeploy.

**`"database":"unavailable"` from the health check.**
`DATABASE_URL` is not bound to `rmpac-db`, or the two services are in different
regions.

**Everyone is locked out after a deploy.**
`SITE_PASSCODE` changed, or was not carried over. Every access cookie is signed
with the passcode itself, so changing it signs all devices out by design. Set it
back, or tell members the new one.

**Rate limited out of sign-in.**
Sign-in allows 8 attempts per email address per 15 minutes. Wait it out, or
redeploy the service — the limiter is in-process, so a restart clears it.

**A published result looks wrong.**
Correct the input and save; the whole season recalculates automatically. Never
edit the database directly — the derived columns are rewritten from the raw
times on every recalculation, so a manual edit would be silently overwritten.

## One known limit

Sign-in rate limiting is held in the web service's own memory, which is accurate
for the single instance this blueprint describes. **If the service is ever
scaled to more than one instance, the limiter must move to the database or a
shared store first** — otherwise each instance counts attempts separately and
the effective limit multiplies. See `src/lib/rate-limit.ts`.
